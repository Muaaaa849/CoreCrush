# ADR 0008 汎用パーティクルは CPU で動かす尾付きの粒（1 本の頂点バッファ・プール）

## 背景
GDD 13 は汎用パーティクル（火花・破片・煙）を「ライブラリで」とし、候補に Three-VFX（WebGPU ネイティブ）、
three.quarks（WebGL。WebGPU 対応 quarks.nodes は実験段階）、TSL コンピュートを挙げる。
本作は WebGPU を既定にしつつ、古い Chrome やスマホでは WebGL2 バックエンドに自動で落ちる（ADR 0001）。
キャッチ・跳ね返し・フェンス通過で一度に出す粒は数十、爆発でも数百〜2,000 程度の見込み。

## 決定
- 自前の `src/vfx/sparks.ts`: 粒の状態（位置・速度・寿命・色）を CPU の型付き配列に持ち、毎フレーム積分して
  **速度方向に伸びたカメラ向きの四角**を 1 本の動的頂点バッファへ書く。1 ドローコール、加算合成。
- 容量は data（`impact.json` の `sparkPool`）で固定し、満杯なら一番古い粒を上書き（試合中に new しない）。
- 衝撃波リングは板をプール（`ringPool` 枚）して TSL で描く（`src/vfx/impactFx.ts`）。
- 粒の向き・ばらつきは描画の演出なので `Math.random` を使う（sim は使わない。判定に影響しない）。
- 軌跡（`ballTrail.ts`）と同じ「CPU で頂点を組む・px の下限で遠くでも潰れない」作りに揃えた。

## 代替案
- three.quarks: WebGL 前提で、WebGPURenderer では実験段階の quarks.nodes が要る。依存が増える割に、今の量では利点が小さい。
- Three-VFX / TSL コンピュート: WebGPU では速いが、WebGL2 フォールバックでコンピュートが使えない（両方の経路を持つ必要）。
- InstancedMesh＋TSL で頂点側に積分: 粒ごとの初期値を属性で渡せば GPU 側で動かせる。爆発で粒が 1,000 を超えて CPU が重いと分かったら移る。

## 不変条件への影響
- コアの可読性: 輪・火花の HDR はコアの顔（faceHdr）未満を validate-data で検査。寿命は 0.5 秒未満。
- sim は触らない（イベントを読むだけ）。ヒットストップは入れていない（Q-11 未回答。提案どおり sim は止めない）。

## 撤回条件
- 爆発（最大 2,000 粒）で CPU の更新が 1ms を超える、またはスマホの基準機で手順6 の予算を超える → GPU 側の積分（InstancedMesh か コンピュート）へ。
